Ulanzi AU05（VibeKey）设备协议

键盘 + 旋钮 + 麦克风一体的语音键盘，USB 无线接收器连接。本文是上位机侧能观测到的全部协议与实测行为。

2. 厂商通道（0xFFFC）：帧格式与 TEA

2.1 组帧

明文（64 字节）
┌──────┬──────┬──────┬──────┬─────────────────────────┬──────────┐
│  b0  │  b1  │  b2  │  b3  │      payload（≤ 60B）     │  补 0 到 64│
└──────┴──────┴──────┴──────┴─────────────────────────┴──────────┘
        │
        ▼  TEA-ECB，32 轮，8 字节一块，字是小端
密文（64 字节）→ 只发前 63 字节 → HID 层再前置 report id 0x55
TEA 密钥（固定）CAA5BACA BC2A8A6D CA5A9EBA 9BB88BCA
delta0x9E3779B9
轮数32 移植
模式ECB，逐 8 字节块；末块不足 8 字节就原样保留
密钥是全局固定、不分设备的——等于没有任何鉴权。任何程序插上就能读写设备配置。这是移植自 OpenVibeKey 的事实，不是我们的选择。

2.2 方向与响应匹配

字段读（GET）写（SET）说明
b00x01（heartbeat 用 0x06）命令大类
b1命令 ID响应里会回显
b2子命令 ID响应里会回显
b30x010x04方向位（个别命令例外，见命令表）
  • 设备响应：解出来的明文里 b0 最高位为 1，且 b1/b2 回显请求值——上位机就靠这两个字节配对响应。
  • 响应数据 = 明文去掉前 4 字节头，即 plain[4:]。
  • 超时窗口默认 0.8 秒（VibeKey.request()）；分片类命令（SN/UUID）用 collect() 收 0.6 秒窗口内的多帧再拼。

4. 按键槽、键位映射与两套存储

设备有 4 个可配置按键槽，每个槽有两套互相独立的存储：

槽物理键0x50 快捷键0x10 原厂固定功能
0btn1（语音键 / 麦克风图标）可写（见 §8.5 的坑）0x6f = 语音 实测·迁移前
1btn2（确认键）可写确认
2btn3（取消键）可写取消
3旋钮按下可写—

4.1 写快捷键（0x50）

payload = [ slot, 0x01, num, (pageSign, value) × num ]
清空     = [ slot, 0x01, 0x00 ]
  • 一条快捷键最多 4 个条目（至多 3 个修饰键 + 1 个主键），官方 App 同款约束。
  • pageSign：bit7 = 左右修饰（1 = 左），低 7 位 = page。写的时候 (page & 0x7F) | (0x80 if 左)。
  • 读回来的格式：[slot, ?, num, (pageSign, value) × num]。键表之外的条目（比如原厂给 btn1 塞的 fn/🌐）不猜，原样显示成 ?page:value。
  • 写 0x10 = 0 会清掉该槽的原厂语义；推荐顺序是先清 0x10、再写 0x50，中间留 120ms——不留固件会丢帧。移植

6. 音频（UAC）

  • 麦克风在键盘本体上，音频经接收器转发；对主机就是个标准 UAC 输入设备，CoreAudio 里名字是 AU05。
  • 设备暴露 2 个输入通道、48kHz；我们按模型需要的 16kHz 单声道采集（CoreAudio 负责重采样）。
  • 接收器插拔之后 CoreAudio 的设备编号会变，缓存的编号就失效了——所以每次录音前都要重新解析。
  • PortAudio 的设备表是缓存的，插拔不会自动刷新。不改这一点，插拔后会拿着一个已经不存在的设备去打开，报 -10851 (Invalid Property Value) 再 -9986。实测 见 §8.2。

7. 电源与待机

待机阈值300 秒（命令 getStandbyTime 读回）实测
触发条件闲置（没有按键、也没人问厂商通道）达到阈值
进待机后的现象厂商通道完全不应答
怎么唤醒按一下键。但那一按会被设备自己吞掉，要按第二次才有报文 实测
心跳能唤醒吗不能。发了 heartbeat 再问，仍然不应答 实测
待机和真关机，上位机能观测到的信号完全一样——这是本节最重要的结论。
待机真关机接收器拔掉
HID 枚举能看到接口是是否
键盘集合能打开是是否
CoreAudio 里有 AU05是是否
厂商通道应答否否接口不存在
发 heartbeat 能唤醒否否—
所以上位机只能说「设备待机/关机中」，不能二选一。只有「接收器拔掉」是能确定性判定的（HID 枚举直接没了）。

8. 实测的坑

这一节是整份文档里最值钱的部分——协议本身很干净，麻烦全在系统侧和设备状态机上。

8.1 键盘集合是独占的：我们一打开，macOS 就收不到这台设备的按键

对照实验（同进程双通道、带时间戳）证实：我们的进程一读这个键盘集合，系统就收不到该设备的按键报文—— 谁先打开谁独占。后果是设备上那两颗普通键（确认 = 回车、取消 = 退格）在前台应用里完全没反应。 所以报文既然只到我们手里，就由我们转发给系统（合成一次键盘事件）。 实测·迁移前 · 双向验证过（不转发时系统确实收不到；转发后按一次只触发一次，不会双字符）

8.2 接收器插拔：HID 立刻能感知，音频那边完全不知情

HID 那条路每次都重新枚举，所以拔掉立刻能发现；但音频走 PortAudio，而 PortAudio 在初始化之后会把设备表缓存住，插拔不刷新。于是 query_devices() 照样把 AU05 报在旧编号上， 上位机拿着一个底层已经不存在的设备去打开 → -10851 → -9986。 必须 sd._terminate(); sd._initialize() 重新枚举才能恢复。 实测

8.3 插回之后有约 3.6 秒「句柄拿到了但设备不发报文」

键盘集合能打开只是个句柄，不等于设备已经在发按键报文。实测插回接收器后： 集合打开 → 接下来约 3.6 秒一个报文都没有 → 之后才正常。用户正好在这段时间按键，就是「按了没反应」。 对策是打开之后先做一次「设备真的能用了吗」的探针，通过才对外报「已连接」。 实测

8.4 待机时第一次按键被吞

见 §7。这条是产品级的：闲置 5 分钟后回来按的第一下不会有任何反应，第二下才生效。

8.5 改键位映射的三个坑

  • 0x50 写进去要插拔接收器重新枚举才生效。实测·迁移前
  • 不要把 0x10 清成 0 就以为完事——清错会导致整颗键哑掉。实测·迁移前
  • 语音键（槽 0）的 0x50 即使插拔也仍然发原生 0x0b，优先级被 0x10 的 0x6f 压住。所以触发语音键只能靠读键盘集合，改映射这条路走不通。实测·迁移前

8.6 官方 Ulanzi Studio 会抢会话

实测 Studio 开着时我们仍能打开厂商通道并读写，但两边同时写配置会互相覆盖。 排障时先确认 Studio 没在跑。实测·迁移前

8.7 两个进程同时问厂商通道会互相吃掉响应帧

厂商通道的响应是靠 b0/b1/b2 匹配的，没有会话 ID。多个进程同时探测时， 谁的 read() 先拿到帧，另一边的响应就被吃掉了，表现为「明明在线却问不到」。 我们为此没让监控脚本和常驻程序同时探测。推断（现象与机制吻合，未做严格的对照实验）

8.8 待机阈值和我们自己的探测会打架

待机是「300 秒没人理就睡」。上位机曾经每 3 秒问一次厂商通道（一天两万多次请求）， 怀疑这会一直把它吵醒、让它永远进不了待机，白耗它自己的电池。 现在改成只在按键那一刻读一次（用户拍板）：按键时设备必然活跃，这时候读最准也最省， 空闲时一概不问。连带代价是「电量/充电状态」只在听写时更新（旧数据不拿来当判据）。 推断（「厂商流量算不算它的活动」这一点始终没做对照验证—— 既然改成不探了，这个问题也就不重要了）

PYTHONPATH=src .venv/bin/python tools/device_probe.py raw 0x0b 0x89
