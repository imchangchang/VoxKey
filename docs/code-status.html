1. 一句话说清整个程序

按键报文从 HID 进来，录音从麦克风进来，两路汇到主程序；主程序起线程录音，边录边把预览文字甩给悬浮条；松手后把整段音频喂给离线模型，解出文字，用 AX 或合成按键打进光标。

设备(接收器) ─┬─ HID 键盘集合 ──→ DeviceKeyReader(线程) ──→ on_key_state()      按键/松手/取消
              └─ UAC 麦克风 ────→ Recorder(sounddevice 回调) ──→ chunks 队列     音频块
                                      │ 每 0.8s 踢一次预览(线程)
                                      ▼
                                 Decoder(funasr-nano, 加锁串行)
                                      │ 松手
                                      ▼
            handle_utterance(线程)：停流 → 判「有没有说话」→ 解出全文 → Injector → 打进光标
                                      │
                                      ▼
            tick_(NSTimer 0.12s)：状态机 → 悬浮条(pill) / 菜单栏图标 / 收场提示

线程一共 5 类：主线程（AppKit）、按键读取线程、录音回调线程（PortAudio）、预览解码线程、每次说话一个的 utterance 线程。共享状态全部走 self.state + state_lock，模型访问走 Decoder._lock。

3. 每个模块现在是什么样

app.py —— 主程序（1220 行，最大的一个）

三个职责，都在一个类（TrayApp）和一个看守线程（KeySupervisor）里：

职责入口现状
按键状态机on_key_state()按下起录、松手出字、取消键丢弃；确认/取消两键转发给系统（因为键盘集合被我们独占，不转发系统就收不到）
说话全流程handle_utterance()录音前重新解析麦克风（插拔后编号会变，变了就重枚举 PortAudio）→ 松手后停流 → 存档 → 说话检测 → 解码 → 上屏 → 收场提示
设备看守KeySupervisor每 2 秒查一次接收器：拔了报「未连接」、插回来自动重开句柄并等设备应答（插回后约 3.6 秒内设备不发报文）；每 3 秒问一次厂商通道判断「待机/关机」；每 2 秒复查权限
UI 刷新tick_()NSTimer 0.12s：算状态 → 悬浮条显隐/文字/角标 → 菜单文案 → 收场提示倒计时 → 淡出

悬浮条显隐规则（pill_wanted()，纯函数，可断言）：听写中/处理中、设备没连接或还在探测、暂停、权限缺失、刚上屏失败 3 秒内、充电中 → 显示；其余收起。

收场提示（_set_linger）：消失前先亮 1.2 秒收场文字再淡出——上屏完成→「空闲」白、设备开机→「已开机」绿、连上→「已连接」绿、恢复监听→「已恢复监听」绿、没听清→「没听清」黄。

已知不干净的地方：TrayApp 一个类干了太多事（1200 行里 60 个方法），状态机、UI、设备探测混在一起；device_off 的判定依赖字符串原因；菜单文案每 tick 无条件重设（已测 ~0.3ms/s，小）。

pill.py —— 悬浮条（653 行）

架构（照开源刘海应用学的）：窗口建一次就不再动（580×172），胶囊是 CALayer，尺寸/位置用 CASpringAnimation 在系统渲染服务里插值，Python 主线程只在状态变化时设一次目标值。

机制现状
布局状态行（居中）+ 内容行（听写预览，最多 6 行，超长保留最近说的并加省略号）。左右角标（左固件版本、右电量/电压）两边对称留宽，中间状态组才是真居中
裁剪胶囊阴影层 + masksToBounds 裁剪层两层结构；内容用中心锚点定位，弹簧参数与胶囊一致，所以内容永远在框内、屏幕位置不动
显隐显示 = orderFront + 重置 alpha；收起 = 0.28s 淡出（带代号防串台，淡出中途 show 不会被老回调收掉）；隐藏期间不建 30fps 定时器
省电30fps 定时器只在「有波形」或「呼吸态」时开；空闲必停（曾因拿常量当状态判断导致永不停，修过）
测量缓存文字宽度按（字号,文本,可用宽）缓存，超过 96 条整体清空

inject.py —— 上屏（359 行）

两级，都不碰剪贴板：

  1. AX 直写：写焦点控件的 kAXSelectedText，回读校验，写完 text 必须出现在新值里才算成功。已知不支持的 App（终端系、Electron/Chromium 系，按 bundle id 列表）直接跳过。
  2. 合成 Unicode 按键：按 UTF-16 切 16 字符块（代理对不切开、块首不接换行），块间 8ms、尾部 25ms；需要「辅助功能」的合成按键权限。

松手前会把之前切走的前台 App 拉回来（防止字打进别的窗口）；密码框 / Secure Input 期间直接拒绝并说明。

audio.py —— 采集（272 行）

  • 100ms 一块，PortAudio 回调里只入队 + 算 RMS。
  • 说话检测（has_speech）：先用 1/10 分位估这段音频自己的底噪，再数高于底噪 3 倍的 20ms 帧总时长。门槛：有效语音 ≥ 0.35s 且峰值 ≥ 0.03。预览和最终解码都过这道闸——没听到人说话就不喂模型，否则它会脑补出「嗯。」。阈值是拿 100 多条真实按键录音标定的。
  • 预览自己滚动提交：每攒够 6 秒把这段解出来接进预览文本，尾巴窗口只覆盖没提交的部分（8 秒）。每轮重解代价从 20 秒降到几秒，预览跟得上说话。间隔按上一轮实测耗时自适应（×1.25，上限 3 秒）。代价：预览文字与最终文字差 4.7%（切分粒度不同）。
  • 录音期间就定稿满段（22 秒一段，切点挑停顿）：松手后只解剩下那段。实测 44 秒语音松手后解码 3176ms → 218ms。
  • 麦克风插拔后 PortAudio 设备表是旧的，要 _terminate/_initialize 重新枚举，否则拿旧编号去开会报 -10851/-9986。

transcribe.py + models.py —— 推理（237 行）

  • recognizer 不能并发（并发会 malloc abort），Decoder 全程加锁。
  • 模型上下文 512 token ≈ 28 秒，长音频按 22 秒切段、切点挑能量最低处（不停在字中间）。
  • 默认模型 funasr-nano-int8（972MB，含 Qwen3-0.6B tokenizer）；注册表里还有 sensevoice、zipformer×2、paraformer 用于质量对比。
  • 解码速度实测约 14 倍实时（4s→287ms，20s→1464ms），线性于音频长度。
  • 模型缺失/名字错抛 ModelNotAvailable（不能用 sys.exit——那会绕过后台线程的 except）。

device/ —— 设备层（701 行）

接收器在 USB 上是复合设备：接口 2 是标准 HID（report 3 键盘），接口 3 是厂商私有通道（usage page 0xFFFC、report 0x55、63 字节、TEA-32 轮加密、密钥全局固定）。

  • keyreader：读键盘报文（9 字节 = report id + 修饰位 + 6 个键码）。语音键原生 0x0b；掉线（拔接收器）hidapi 会抛 OSError，现在会记下原因并让看守重开句柄。
  • device/protocol：12 条命令（版本/电量/SN/UUID/麦克风开关/键位/固定功能/钩子模式/待机时间/指示灯/心跳）。电量响应 59 字节，电压 u16le@0、百分比@2（10% 一档的粗表）、充电标志@6。
  • device：传输层。响应靠 b0 最高位 + b1/b2 回显匹配；分片类命令收 0.6 秒窗口拼帧；待机时间实测 300 秒。
  • 电源状态：厂商通道不应答 = 待机或关机（区分不了，连发 heartbeat 也叫不醒）；只有接收器拔掉能确定性判定（HID 枚举直接没了）。

tools/ —— 工具（1163 行）

smoke.py 16 项自检（包导入、悬浮条几何、长预览裁剪、显隐规则、收场提示规则、说话检测闸门、淡出、角标、模型、4 个 CLI --help），不连设备、不要权限，改完代码必须跑。device_probe.py 读写键位、发原始命令。verify/ 用 say 生成的语料对比候选模型的 CER/延迟。

5. 已知问题 / 没做的事

问题状态
待机和真关机无法区分：现象完全一样（HID 在、键盘集合能开、AU05 在、厂商通道沉默、心跳叫不醒）提示合并为「设备待机/关机中」；按键报文一到就自动翻回在线
待机时第一次按键被设备吞掉（要按第二次才生效）固件行为，软件侧无解；悬浮条提示让用户知道要按两下
预览文字与最终文字差 4.7%（切分粒度不同，用户已接受）要消除只能换流式模型做预览（+531MB 内存）或接受更慢的刷新
预览更新间隔随音频变长退化（0.8s → 1.5~3s，负载高时更慢）已做自适应间隔；根治要流式模型或更快的离线模型
远程桌面/虚拟机丢 Unicode 载荷（会打出一串 a）；密码框/Secure Input 期间注入无效平台限制，软件层无解，只能拒绝并提示
只支持主屏（副屏拖动会被拉回、文字缩放取主屏）未做
单实例锁在临时目录；还没打包 .app（权限归属、开机自启、签名公证）未做，打包时一起处理
模型常驻 ~1GB，超目标issue #14 待拍板（候选：换更小模型/闲时卸载）
TrayApp 1200 行、60 个方法，状态机/UI/设备探测混在一个类里能跑但难改；若上 Rust 自然重划

6. 怎么跑、怎么验、日志在哪

python3.12 -m venv .venv && .venv/bin/pip install -e '.[tools]'
PYTHONPATH=src .venv/bin/python -m voxkey.app          # 常驻
PYTHONPATH=src .venv/bin/python tools/smoke.py         # 自检（16 项，不连设备）
  • 模型放 models/（972MB，gitignore），或 VOXKEY_MODELS_DIR 指别处。
  • 日志：常驻程序 stdout 重定向到 voxkey.log（仓库根目录，已 gitignore——别再放 /tmp，被系统清过一次）。
  • 权限三样：麦克风、辅助功能（合成按键 + AX）、输入监控（读设备按键）。脚本形态权限记在启动它的终端头上。
  • 按键上报的原始报文：--debug-keys；录音存档：--save-audio 目录（wav + index.jsonl，带时长/RMS/峰值）。
  • 设备协议细节（厂商通道、命令表、键位表、实测坑）另见 docs/au05-protocol.html。

数字都能在提交记录和运行日志里找到对应证据。没有写「待优化」却没数据支撑的条目。
